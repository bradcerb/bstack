# Project brief

One page to start a real project without boiling the ocean. A project here means a large initiative that produces a unique result and has an end point. It is not every two-step chore. Small one-off tasks belong on an actions list, not in this brief.

Portable across agents. This skill declares no config. Filing a ticket or a page is a later request, outside this brief.

## Principle

Name the purpose and success measure before tactics. Keep projects few enough to finish (about four to seven active large initiatives in a life domain is a useful ceiling). Put the first finish line on this week's plan. Leave slack. Ship when the outcome gate is met.

## Inputs

- Project name or rough intent
- Who is served and what unique result changes
- Constraints (time, money, skills, protected windows, other active projects)
- Optional: notes or requests the human pastes in

If the ask is only a vague topic, ask for the intended result before drafting a long brief. If the work is truly a small action, say so and stop; do not inflate it into a project.

## Rules

- Draft only. Do not create tickets, send outreach, spend, or publish unless asked.
- Outcome and out-of-scope matter as much as in-scope.
- Milestones are finish lines with checkable results, not activity piles.
- Prefer the smallest reversible first finish line.
- Route uncertainty: disclose low-cost assumptions; show branches before heavy reversible investment; pause before purpose, authority, commitment, or external-risk assumptions.
- Never use em-dashes.

## Steps

1. **Purpose** - Name the project, who it serves, and the success measure (what an observer would see when the unique result is done).
2. **Principles** - List a few governing standards for how the work will be carried out (quality floor, constraints, non-negotiables). Keep short.
3. **Scope in / not doing** - In scope as concrete deliverables or decisions. Out of scope as an explicit not-doing list for this effort.
4. **Actions as stages** - Outline 3 to 5 finish lines (stages) with rough dates and checkable results. First stage should prove the path and fit as a slice on this week's priority list. Leave slack; do not schedule at full capacity. Do not hold the brief for optional polish past the outcome gate.
5. **Info, risks, waiting** - Capture key facts, barriers, dependencies, and anything you are waiting on from others. Treat a requested deliverable as a hypothesis when the real problem is unclear; pause or branch instead of pretending certainty.
6. **Next action** - One concrete next step that starts stage one, plus what done looks like for that step. If useful, note where the project sits relative to other active initiatives (is there room, or must something else be reduced?).
7. **Stop** - Deliver the one-page brief. Do not file tickets unless asked.

## Output shape

```
## Project brief - [Name]

### Purpose
- Serves: ...
- Success measure: ...

### Principles
- ...

### In scope
- ...

### Not doing (out of scope)
- ...

### Actions (stages / finish lines)
1. [Result] - rough date
2. ...

### Info / risks / waiting on
- ...

### Next action
- Action - done looks like: ...
```

## Anti-jobs

- Do not turn every multi-step chore into a project brief.
- Do not import an org PM process or client account rituals into the brief.
- Do not expand mid-draft into full weekly planning or inbox processing without an asked handoff.
- Do not treat activity volume or polish as the success measure when an observable result exists.

## Completion

One-page brief ready to paste (purpose, principles, actions, info). Stages can feed weekly priorities and gated work. Draft only.
